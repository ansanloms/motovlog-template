# ADR-0001: 動画作成に Remotion を使う

## Context

既存のモトブログ動画は AviUtl (拡張編集) と PSDToolKit で作成している。動画の構成は、台本があり、その各行に立ち絵 (PSD)、字幕、VOICEVOX で合成した音声が並ぶ定型である。背景には Insta360 で撮影した走行映像が流れる。

GUI 編集での制作には次の問題がある。

- 立ち絵・字幕・音声の配置を、セリフの数だけ繰り返し手で入力する。
- 台本を 1 行直しても音声・字幕・口パクに変更が伝播せず、手で作り直す。
- プロジェクトファイルを diff できず、何を変えたか追えない。

制作工程を CLI/TUI 寄りにしたい要望と、道具を自前で持ちたい要望がある。前者は効率を、後者は自作を基準とし、両者を混同しないことを確認した上で検討した。ツールのライセンスは可能なら OSS が望ましいという条件があった。

検討は AviUtl2 の Rust プラグイン (PSD の口パク・目パチ、VOICEVOX API 連携) を作る案から始まった。

## Decision Drivers

1. 台本から立ち絵・字幕・音声の配置が機械的に導出できること (定型の動画を数多く作る)
2. 台本の変更が音声・字幕・口パクへ伝播し、変更を git で diff できること
3. レンダリングが CLI で完結すること
4. 字幕の見た目や立ち絵の動きを自分で書けること (ツールではなくフレームワークであること)
5. VOICEVOX と立ち絵を組み合わせた先行事例があり、詰まったときに参照できること
6. OSS ライセンスであること (個人利用の無料枠で妥協できる)

## Considered Options

1. Remotion — 採用。React コンポーネントとして動画を書き、CLI からレンダリングできる。台本の各行を配列で回して機械的に並べるモデルが定型動画に合う。台本もレイアウトもコードとテキストになるため git が効く。VOICEVOX と立ち絵を組み合わせたテンプレートが複数公開されている。ライセンスは OSS ではないが、個人利用は無料で商用も許可されている。
2. AviUtl2 + 自作 Rust プラグイン (口パク・目パチ・VOICEVOX 連携) — 却下。口パク・目パチは PSDToolKit2 が AviUtl2 対応済みで、自作は既存品の再実装になる。GUI 編集の 3 つの問題 (反復入力・伝播不能・diff 不能) はプラグインでは解決しない。AviUtl2 本体は OSS ではない。
3. AviUtl2 を残し、台本から `.aup2` プロジェクトファイルを CLI で生成する — 却下。`.aup2` のフォーマットは有志の非公式調査に依存し、仕様変更を追えない。プレビューと微調整が GUI に残るため、diff 不能の問題も残る。
4. ffmpeg ベースの自前レンダリングパイプライン (Rust) — 却下。合成・タイムライン表現・フォント描画・プレビューをすべて自前で作ることになり、スコープが大きすぎて完成しない可能性が高い。
5. Kdenlive/Shotcut (MLT) のプロジェクト XML を CLI で生成する — 却下。OSS であり、MLT XML には文書と DTD があり `melt` で CLI レンダリングできる点は優位である。しかし日本語圏の立ち絵動画のエコシステム (口パク・目パチ・字幕) が無く、すべてゼロから C の API で作ることになる。
6. Motion Canvas/Revideo — 却下。MIT ライセンスである点が唯一の優位。レンダリングの起動がエディタ UI のボタンで CLI 指向に反する (Revideo は関数呼び出しで可能とされるが、保守状況を確認していない)。アニメーションを逐次記述するモデルで、台本駆動の量産に合わない。VOICEVOX と立ち絵の先行事例が見当たらない。

## Decision

- 動画の組み立てとレンダリングに Remotion を使う。動画は React (TypeScript) のコンポーネントとして記述する。
- レンダリングは Remotion の CLI で行い、GUI 編集ソフトを工程に置かない。
- 動画の内容 (台本・素材の割り当て・レイアウト) はコードまたはテキストデータとしてリポジトリで版管理する。
- Remotion の実行環境として Node.js を使う。
- Remotion のライセンスは個人利用の無料枠 (Free License) の範囲で使う。4 人以上の営利組織での利用に変わる場合は本 ADR を見直す。

## Consequences

### 利点

- 台本もレイアウトもテキストになり、変更が diff で読める。
- 台本の変更が音声・字幕・口パクへ機械的に伝播する構造を作れる。
- レンダリングが CLI で完結し、自動化できる。
- 字幕・立ち絵・映像の各要素を自分で書くため、自作の余地が広い。
- Remotion と VOICEVOX を組み合わせた先行事例を参照できる。

### 代償

- Remotion は OSS ではなく source-available で、Remotion 自体を製品として販売できない。将来の条件変更に対して fork で対抗できない。
- タイムラインをドラッグして直す GUI 編集は無い。演出の試行錯誤はプレビューとコード修正の往復になる。
- レンダリングは Headless Chrome でフレームを描く構造のため時間がかかる。持続レンダリングの実測は約 0.22 秒/フレーム。
- 長尺・大容量の HEVC 素材は直接読めず、H.264 のプロキシへ事前変換する工程が要る。
- Node.js が必須になる。
- AviUtl2 プラグイン開発と Rust で得る予定だった知見は対象外になる。

### 禁止事項

- 動画の組み立てを GUI 編集ソフトのプロジェクトファイルで管理すること。
- Remotion 自体を製品として販売すること、およびライセンス購入を回避させる形で提供すること (ライセンス条件)。

## Assumptions

| 前提                                                             | 状態   | 確認方法 / 結果                                                                                                                                      |
| ---------------------------------------------------------------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 通常の尺の動画でレンダリング時間が試行錯誤を妨げない範囲に収まる | 未検証 | 実際の動画で台本からレンダリング完了までの時間を計測し、AviUtl での制作時間と比較する。持続レンダリングの部分計測 (2026-09-02) は約 0.22 秒/フレーム |
| Remotion の個人利用無料枠が継続する                              | 未検証 | Remotion をバージョンアップするたびにライセンス FAQ を確認する                                                                                       |
| 作る動画が「台本 + 立ち絵 + 字幕 + 音声」の定型に留まる          | 未検証 | 数本作った後に、カットごとの演出の作り込みが必要になっていないかを振り返る                                                                           |
