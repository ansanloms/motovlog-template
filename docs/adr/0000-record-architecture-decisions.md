# ADR-0000: 設計上の決定を ADR として記録する

## Context

設計上の決定とその背景が会話ログ・PR コメント・個人の記憶に散らばると、後から「なぜこの構成になっているか」を辿れない。決定を覆す際にも、当時の判断基準と却下した選択肢が分からず、同じ検討を繰り返すことになる。

このリポジトリでは、動画作成の方式や動画管理の構成に関する決定が GitHub の issue・PR と claude.ai の会話に分散している。issue と PR はリポジトリに紐づくため、別リポジトリへ移行すると引き継げない。

## Decision Drivers

1. 決定の背景 (状況・判断基準・却下した選択肢) を後から辿れること
2. リポジトリを移行しても記録が一緒に移ること
3. 記録のコストが低く、運用が続けられること

## Considered Options

1. ADR (`docs/adr/` に markdown で記録) — 採用。コードと同じリポジトリで版管理でき、テンプレートで粒度を揃えられる。リポジトリの移行時にファイルごと移せる。
2. wiki・外部ドキュメントツール — 却下。コードと分離し、変更履歴の追跡が別系統になる。
3. 記録しない (issue・PR・会話ログに任せる) — 却下。横断的に探せず、却下した選択肢が残らない。issue と PR はリポジトリの移行で失われる。

## Decision

- 設計上の決定を `docs/adr/NNNN-<要約>.md` に ADR として記録する。NNNN は 4 桁ゼロ埋めの連番とし、欠番は再利用しない。ファイル名の要約は英語またはローマ字の kebab-case (ASCII) で書く。
- ADR にするのは次のいずれかに当たる決定 (以下、閾値) とする。
  - 層の境界・データモデル・外部依存 (ライブラリ・フレームワーク・外部サービス・ライセンス) に触れる決定
  - 覆すと既存コードの書き直し、または保存済みデータの移行が要る決定
  - 「やらない」と決めたこと (スコープの切り捨て)
- 命名規約やフォーマッタ設定など、変えても影響が局所的な決定は ADR にしない。
- status は次の順にだけ遷移させる。本文を変更できるのは proposed の間だけとし、決定を覆すときは新しい ADR で supersede する。
- 例外として、accepted の ADR でも、その決定に基づく成果物 (実装・素材・動画) がまだ無い間は Decision を書き換えてよい。書き換えたときは date を更新し、References に変更の日付と内容を残す。成果物ができた後の変更は supersede に限る。
  - proposed から accepted または rejected へ
  - accepted から deprecated または superseded へ
  - deprecated から superseded へ

## Consequences

### 利点

- 決定の背景と却下した選択肢がリポジトリ内に残り、後から辿れる。
- 決定を覆す際の影響 (Consequences・Assumptions) が明文化されている。
- リポジトリを移行しても記録が失われない。

### 代償

- 閾値を超える決定のたびに ADR を書くコストが掛かる。
- issue・PR に散在する既存の決定を ADR へ起こし直す作業が要る。

### 禁止事項

- accepted の ADR の本文を書き換えること (Assumptions の「状態」列の更新を除く)。
- 閾値を超える決定を ADR なしで実装へ持ち込むこと。

## Assumptions

| 前提                                                             | 状態   | 確認方法 / 結果                                              |
| ---------------------------------------------------------------- | ------ | ------------------------------------------------------------ |
| 閾値を超える決定の頻度は、ADR の作成が運用を止めない程度に収まる | 未検証 | 運用開始後の振り返りで、ADR の作成が滞っていないかを確認する |
